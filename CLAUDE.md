# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Projet

« Usine à vidéos » puis plateforme d'équipe pour un label de musique électronique (Dancing Dead Records). Cœur : transformer un morceau du label + un dossier de clips en un montage vidéo vertical 9:16 (1080x1920, H.264) dont les coupes sont synchronisées sur les beats de la musique. Au-dessus : un dashboard multi-membres où chaque niche relie un preset de montage, une banque de clips et une sélection de sons, et depuis lequel on lance à la demande un lot de N variantes (montages + punchlines différents) qui alimentent une bibliothèque à poster à la main.

Périmètre volontairement borné : **pas de publication automatique** (décision 2026-07-08, voir plus bas), pas de scraping, pas d'heure de programmation. Éviter toute sur-ingénierie.

## Environnement et commandes

Le projet utilise **uv** (pas pip directement — le venv n'a pas de module pip).

```bash
uv sync                          # installer les dépendances
uv run python beatsync.py ...    # lancer le script principal
uv run pytest                    # lancer les tests
uv run pytest tests/test_build_edl.py -k <nom>   # un seul test
```

**FFmpeg est une dépendance système** (`brew install ffmpeg` sur macOS). Le rendu passe par `subprocess` (jamais par ffmpeg-python, non maintenu) ; `ffprobe` sert à lire les métadonnées des clips.

## Architecture

Scripts indépendants :

- `db.py` — persistance SQLite de la plateforme d'équipe (`platform.db`, gitignoré) : tables members/presets/niches/videos. Toutes les fonctions sont pures et testées (`connect`, `slugify` avec translittération NFKD des accents, membres avec mots de passe hachés werkzeug + CLI `add-member`/`list-members`, presets + `effective_config` = `DEFAULT_CONFIG ← settings.json ← preset`, niches avec dossier `.../videos/`, colonnes `tracks` et `clips` = **sélections** de chemins dans les catalogues partagés (`tracks/` pour les sons, `clips/` pour les clips — voir plus bas), videos statut proposed|approved|rejected|posted|failed ; tables `clipper_sources` (une vidéo longue importée, statut pending|transcribing|analyzing|rendering|done|failed) et `clipper_clips` (les shorts qu'elle produit, `source_id` en FK `ON DELETE CASCADE` — supprimer une source supprime ses clips sans code Python dédié, la garantie tient parce que `connect` active `PRAGMA foreign_keys = ON` (SQLite ignore les FK par défaut) — statut proposed|approved|rejected|posted, voir l'entrée `clipper.py` plus bas). `connect` migre les bases existantes (`_migrate` / `_ADDED_COLUMNS` : `ALTER TABLE ADD COLUMN` pour les colonnes ajoutées après coup, ex. `tracks`, `clips` — `CREATE TABLE IF NOT EXISTS` ne met pas à jour une base déjà créée). CLI : `python db.py add-member <nom>`.
- `webui.py` — interface Flask locale (127.0.0.1:8765). `create_app(root=None)` injectable (tous les chemins dérivés de `root`, testable via test_client). Login par membre (session, `before_request` → 401 sur `/api/*`), secret persisté dans `data/secret_key` (0600). Onglets : Niches, Presets, **Catalogue** (ressources partagées du label, deux sections : **Sons** `tracks/` et **Clips** `clips/` — chacune upload + import YouTube ; la section Clips accepte aussi les images (`.jpg .jpeg .png .webp`, constante `CLIP_EXTS`), montées en flash court par `build_edl` ; endpoints `/api/tracks`,`/api/links`,`/api/download` pour les sons, `/api/clips`,`/api/clip-links`,`/api/clips/download` pour les clips ; **rognage** d'un clip via `POST /api/clips/<name>/trim` (tâche de fond `trim_clip.py`, détaillé plus bas), restreint à `TRIMMABLE_EXTS` (= `VIDEO_EXTS` moins `.webm`) et non `CLIP_EXTS` — rogner une image n'a pas de sens, elle n'a pas de durée à couper, et le `.webm` échouait systématiquement : le temporaire hérite du suffixe de la source et le rognage réencode en libx264, que le muxeur WebM refuse (code 234). Le `.webm` reste uploadable, listé et montable ; le retirer de `VIDEO_EXTS` l'aurait fait disparaître du catalogue et du Clipper, et renommer la sortie en `.mp4` casserait les sélections de clips des niches. Le rognage rend aussi **409 tant qu'un job `gen-` tourne** (`running_job_names`) : `load_clips`/`scan_clips` ont déjà lu la durée du clip et l'EDL est calculé dessus — rogner sous leurs pieds donne des segments noirs sous macOS et un `replace` refusé sous Windows. Garde volontairement grossière (toute génération, pas seulement celles qui sélectionnent ce clip) : les générations sont longues mais rares, et le risque est une perte de travail des deux côtés — et nommé par clip (`trim-<nom>`) dans la table de jobs commune : deux clips différents peuvent se rogner en parallèle, mais un double-clic sur le même clip rend 409 plutôt que de lancer deux ffmpeg sur le même fichier ; **suppression** d'un asset partagé via `DELETE /api/tracks/<name>` et `DELETE /api/clips/<name>` — efface le fichier du disque (garde anti-traversal : uniquement un fichier directement sous `tracks/`/`clips/`) ET retire sa référence des sélections de toutes les niches ; un `unlink` refusé — fichier tenu par un ffmpeg de rognage ou de génération, cas courant sous Windows — rend **409** et non 500, et laisse la référence en base puisque le fichier est toujours là), Réglages. Tout est **partagé + sélectionné dans la niche** : une niche relie un **preset** de montage, une **sélection de sons** ET une **sélection de clips** (deux cartes identiques dans le détail niche : ajout/retrait immédiats via `PATCH /api/niches/<id>` `{tracks|clips}`, « retirer » ne supprime pas le fichier du catalogue) + un préprompt de punchlines ; la carte Génération lance un lot de N variantes (`POST /api/niches/<id>/generate`, tâche de fond `generate_niche.py`) et affiche la bibliothèque des vidéos produites (`GET /api/videos/<id>` lecture/`?dl=1`, `POST /api/videos/<id>/status` pour valider/rejeter, `DELETE /api/videos/<id>` supprime ligne + fichier). Onglet **Clipper** (sous-système parallèle, voir plus bas) : upload direct ou import YouTube d'une source vidéo longue (`POST /api/clipper/sources`, `POST /api/clipper/sources/link` — même garde de validation d'URL que le Catalogue, liste blanche de `netloc` YouTube ET rejet de tout caractère d'espacement, parce que l'URL finit dans un fichier que `fetch_tracks.parse_links` découpe **une ligne = un argument** passé à yt-dlp — un espace ou un retour à la ligne y injecterait une option), inbox en deux temps (`GET /api/clipper/inbox` liste les fichiers déposés par yt-dlp sous leur nom d'origine — inconnu avant la fin du téléchargement — puis `POST /api/clipper/inbox/<name>` **déplace** le fichier vers la source et crée la ligne en base), lancement de l'analyse (`POST /api/clipper/sources/<id>/run`, tâche de fond `clip_source.py`, suivie par polling générique `GET /api/jobs/<job_id>`), lecture/suppression des clips produits (`GET /api/clipper/clips/<id>` lecture/`?dl=1`, `POST .../status`, `DELETE /api/clipper/clips/<id>`) et suppression d'une source (`DELETE /api/clipper/sources/<id>` : refusée en 409 tant qu'un job tourne sur la source — statuts `transcribing`/`analyzing`/`rendering`, sans quoi le job recrée les dossiers et écrit des mp4 sans ligne en base — puis `shutil.rmtree` du dossier **avant** la suppression en base (les clips suivent par FK cascade), gardé par une égalité stricte sur le parent : le dossier à effacer doit être un enfant direct de `data/clipper`, sinon un slug vide résoudrait sur `data/clipper` lui-même et effacerait les sources de tous les membres ; un `rmtree` qui échoue (handle ouvert sous Windows) rend 409 et laisse la ligne en place, plutôt qu'un 500 et un dossier orphelin. Corollaire : `clip_source.slug_for` reçoit l'**union** des slugs en base et des dossiers présents sur disque — un dossier orphelin dont le slug serait réattribué ferait hériter la nouvelle source du `transcript.json` de l'ancienne, donc des clips découpés aux timestamps d'une autre vidéo, en silence. `/api/state` projette sources et clips sur une liste blanche de champs (pas de `path`/`file` : l'arborescence disque ne sort pas), comme les vidéos des niches. L'import YouTube passe `--with-audio` et la promotion d'un fichier d'inbox sans piste audio est refusée en 400. Identité visuelle Dancing Dead : noir OLED + accent rouge `#ff1e46`, typo Fira Sans/Code, icônes SVG (pas d'emoji), toasts + modales stylées. Défense XSS : `esc()` sur tout champ STATE rendu via innerHTML + coercion serveur des champs numériques (cadence via `db.update_niche`, overrides via `coerce_overrides`) → 400 si non convertible ; `coerce_overrides` refuse un `format` hors `ALLOWED_FORMATS`, borne les trois valeurs d'`end_scene` (`beats`/`freeze`/`speed`) et celles de `speed_ramp` (`interpolate` en booléen, `slow_beats` entier borné par `SLOW_BEATS_RANGE` = 1 à 8 — au-delà d'`impact_beats` la fusion avalerait toute la grille) et `blackout_beats` borné `[0.25, 2.0]` (en dessous, le clignotement dépasse 4 Hz ; au-delà, ce ne sont plus des éclairs) ainsi que `blackout_lead` borné `[0, 8]`. L'éditeur de preset expose le format de sortie, la scène de fin (activation, beats, figé, vitesse), les ralentis fluides, la longueur du ralenti et le strobe (bascule + cadence + longueur de la montée sans drop). L'onglet Réglages porte une carte « Clipper » (modèle Whisper, nombre de shorts, durées min/max), bornée serveur par `coerce_clipper` — qui refuse aussi `min_dur > max_dur` (l'inversion ne rendrait aucun clip et le `failed` accuserait le recalage). `merge_settings`/`load_settings` vivent dans beatsync.
- **Publication TikTok abandonnée** (décision 2026-07-08) : plus de connexion à l'API TikTok pour la publication auto. `tiktok_auth.py`, l'onglet Comptes et les endpoints `/api/auth/*` ont été supprimés. La sortie de l'usine est une bibliothèque de vidéos à poster à la main. L'app sandbox TikTok et le site callback (repo Hooriiiii/dancingdead-site) restent en sommeil hors du repo.
- `fetch_tracks.py` — télécharge l'audio (mp3, → `tracks/`) OU la vidéo (≤1080p mp4, `--video`, → `clips/` pour le catalogue de clips partagé) des liens YouTube via yt-dlp. `--with-audio` (avec `--video`) muxe la piste audio (`bv*[height<=1080]+ba/b[height<=1080]/b` + `--merge-output-format mp4`) : `bv*` seul sélectionne le meilleur flux **vidéo seule**, un DASH 1080p muet sur YouTube — sans audio le catalogue beatsync s'en moque (d'où le défaut inchangé, sinon tout serait à retélécharger), mais la source du clipper serait condamnée avant la transcription. `parse_links` et `ytdlp_args` sont les parties pures testées.
- `trim_clip.py` — rogne le début et/ou la fin d'un clip du catalogue partagé, EN PLACE. `python trim_clip.py <nom> <début> <fin> [<racine>]`, lancé en tâche de fond par l'UI (`POST /api/clips/<nom>/trim`, voir `webui.py` plus haut). La coupe est **destructive** (le fichier de `clips/` est réécrit) plutôt que des bornes mémorisées et appliquées à la volée : cette seconde option aurait obligé `load_clips`, le scan et son cache à connaître et respecter des bornes par clip — toucher au cœur du montage pour une fonctionnalité de catalogue. Un clip mal rogné se réimporte depuis `clip_links.txt`, au prix d'un nouveau téléchargement. **Réencodage** (`ffmpeg_trim_args`, libx264/`TRIM_CRF`=18/`TRIM_PRESET`=medium) et non copie de flux : les images-clés des clips du catalogue sont irrégulières jusqu'à 5 s d'écart (mesuré) — une copie de flux calerait la coupe sur la keyframe la plus proche et laisserait plusieurs secondes d'intro. `TRIM_CRF` vaut 18 et non le 20 du rendu final : ce fichier est un intermédiaire que le montage réencode une seconde fois, lui laisser de la marge évite d'empiler deux générations de perte. Bénéfice secondaire du réencodage : les clips AV1 du catalogue deviennent du H.264, nettement plus rapide à décoder pour le scan et le rendu, qui les redécodent à chaque génération. `-ss` est placé avant `-i` (comme partout ailleurs dans le projet) : le coût suit la durée de SORTIE et non la taille du fichier source — mesuré, environ deux minutes pour un rognage AV1 typique (199 s de sortie), pas les quelques secondes qu'on pourrait attendre d'une simple coupe de flux. `coerce_bounds` (**pure et testée**) valide les bornes contre la durée réelle lue par `probe_duration` (jamais contre une durée fournie par le client) et absorbe le débordement mineur en fin de lecteur (`END_TOLERANCE`, 0,5 s) sans masquer une vraie erreur de saisie. Le temporaire est écrit dans `clips/.trim/` (`TRIM_DIR_NAME`), un sous-dossier plutôt qu'un fichier voisin : `load_clips` et `/api/state` parcourent `clips/` et prendraient un `.trim.mp4` oublié pour un vrai clip — un sous-dossier en est absent par construction. Son nom porte le PID du process (`{stem}.{pid}{suffix}`) et non juste le nom du clip : deux rognages du même clip peuvent tourner en même temps (double-clic, ou relance d'un job qui paraît figé) et un nom partagé faisait courir à l'un le risque d'écraser le temporaire de l'autre puis de remplacer le clip d'origine par un mp4 partiel. Le remplacement (`Path.replace`, atomique sur le même volume) n'a lieu qu'après un code retour FFmpeg nul **et une vérification de la durée produite** (`probe_duration` sur le temporaire, marge `END_TOLERANCE`) : ffmpeg traite une erreur de démuxage rencontrée en cours de flux comme une fin de fichier — il journalise « partial file », s'arrête là, et **sort en 0**. Sans ce contrôle, un rognage `[5, 180]` sur un clip abîmé promouvait 27 s de vidéo par-dessus l'original et détruisait 140 s de rushes avec un « OK » dans le journal (`-xerror` ne couvre pas le `partial file` du démuxeur, le contrôle de durée si). Le remplacement est précédé d'un `fsync` sur le temporaire ouvert en **`"rb+"`** et non `"rb"` : sous Windows (la tour de prod), `FlushFileBuffers` exige un handle ouvert en écriture et échoue sinon silencieusement en `"rb"` sur macOS/Linux (où `fsync` réussit même en lecture seule) — sans ce détail le fsync aurait été un no-op invisible en local et le rognage inopérant en production dès une coupure survenant juste après le rename. Cette garantie est vérifiée, pas seulement déduite : un `kill -9` en plein encodage laisse le clip d'origine identique bit à bit (même MD5) — le temporaire mort reste orphelin dans `.trim/`, jamais promu. Pas de `rmdir` du dossier temporaire en fin de rognage, volontairement : `clips/.trim/` est partagé par tous les rognages en cours, y compris ceux d'autres clips, et le nettoyage de l'un pouvait supprimer le dossier sous les pieds d'un autre qui venait de le créer et de lancer ffmpeg sans y avoir encore écrit — panne non reproductible et sans rapport apparent avec le rognage fautif. Un dossier `.trim` vide est de toute façon invisible de `load_clips` et `/api/state`, donc le nettoyer ne rapporte rien — mais son CONTENU hérite de cette même invisibilité tout en pesant des centaines de mégaoctets par temporaire mort (`kill -9`, coupure de courant, `replace` refusé), et le premier symptôme aurait été une génération qui échoue sur disque plein : `purge_temporaires` supprime donc, en tête de chaque rognage, les fichiers de `.trim/` vieux de plus de `TRIM_MAX_AGE` (24 h, très au-dessus du rognage le plus long, donc jamais celui d'une exécution en cours). Le `finally` distingue les **trois issues** : ffmpeg en échec (temporaire supprimé — un fichier partiel n'a aucune valeur), `replace` refusé (temporaire **conservé** et son chemin nommé dans l'erreur : c'est le mode d'échec attendu sous Windows, antivirus/indexeur/lecteur/génération qui tient un handle, et le seul où le fichier produit est bon — le jeter obligerait à recommencer deux minutes d'encodage avec la même probabilité d'échec), succès (plus rien à supprimer). Un `unlink` refusé après un `replace` réussi est journalisé, jamais levé : il ne dit rien du rognage, qui a abouti. Le **nom de fichier ne change pas** : les sélections de clips des niches (qui référencent `clips/<nom>`) survivent au rognage sans mise à jour. Le **cache de scan se périme tout seul** (`scan_clips(cache_dir=...)` invalide par mtime) puisque le rognage réécrit le fichier — aucune invalidation manuelle à ajouter côté `trim_clip.py`. Le rognage est refusé en **409 tant qu'une génération tourne** (n'importe quel job `gen-`, voir `webui.py`). Défaut connu et non corrigé : rien n'interverrouille le rognage et la suppression d'un clip — supprimer un clip pendant son rognage laisse le remplacement final recréer le fichier, désormais orphelin d'aucune niche ni intention. L'UI le rend difficile à atteindre (boutons de la ligne désactivés pendant l'opération, verrou porté par un état levé au-dessus de l'onglet Catalogue donc qui survit à un changement d'onglet) mais un rechargement de page perd cet état et rouvre la fenêtre. Côté front, une **perte de suivi n'est pas un échec** : `JobLog` signale les deux cas séparément (`onLost` optionnel, sinon repli sur `onDone("failed")` pour les appelants non destructifs), et un rognage dont le suivi est perdu reste verrouillé — cinq sondages en erreur ne valent que 7,5 s de serveur muet (recyclage de waitress, hoquet Tailscale), là où l'encodage dure deux minutes : déverrouiller la ligne poussait à relancer un rognage en cours, dont le second ffmpeg repartait du fichier DÉJÀ rogné par le premier. Le toast d'un échec réel dit que le clip d'origine est intact, la seule information qui décide si on peut relancer.
- `generate_niche.py` — orchestrateur de **lot par niche**. `python generate_niche.py <niche_id> <count> [<root>]` : lit la niche en base, charge ses **clips sélectionnés** depuis le catalogue partagé `clips/` (filtre `niche["clips"]`) et les scanne une fois (cache mutualisé entre niches), puis pour chaque variante tire un couple `(morceau, seed)` distinct (`plan_variants`, pure & testée — seeds distinctes, morceaux pris parmi ceux sélectionnés dans la niche), alterne les presets liés, fusionne `settings.json ← preset`, applique les `subtitles` de la niche, et appelle `beatsync.generate_video` dans `data/niches/<slug>/videos/`. Chaque vidéo produite est enregistrée en base (`db.create_video`, statut `proposed`, punchlines stockées dans `subtitles.lines`) → une même niche donne N variantes au montage ET aux punchlines différents. `video_stem` (pure) construit un nom de fichier sûr. Lancé en tâche de fond par l'UI (bouton « Générer »). Il n'y a pas d'heure de programmation : on lance la génération quand on veut.
- `clipper.py` / `clip_source.py` — **second front de l'usine**, indépendant de beatsync : d'une vidéo longue parlée (interview, live, stream) vers une bibliothèque de shorts 9:16 recadrés, sous-titrés et classés par pertinence — pas de synchronisation aux beats, pas de musique. Pipeline dans `clip_source.py` (`process`, orchestrateur, comme `generate_niche.py`) : transcription (`clipper.transcribe`, faster-whisper, **mise en cache sur disque** dans `<source>/transcript.json` et jamais recalculée — de très loin l'étape la plus lente ; un cache corrompu vaut cache absent, même convention que `beatsync.scan_clips`, sinon un process tué en pleine écriture condamnerait la source pour toujours) → proposition de moments par LLM (`clipper.propose_moments`, sur-demande ×1,5 car le recalage en rejette une partie) → recalage sur des frontières de phrase (`clipper.snap_to_speech`, s'appuie sur `sentences` — une phrase se termine sur une ponctuation forte OU un blanc ≥ `SENTENCE_GAP` (0,6 s) : Whisper ponctue mal le français parlé, le silence est un signal plus fiable ; retourne `None` si l'extrait ne rentre pas dans `[min_dur, max_dur]`, mieux vaut un clip de moins qu'un clip qui commence au milieu d'un mot) → notation (`clipper.score_moment`, trois notes hook/flow/value pondérées par `WEIGHTS`, le hook pèse le plus car c'est la seule des trois qui décide du scroll) → classement (`clipper.rank_moments`, pure et testée, écarte les doublons de position via `_overlap_ratio` > `OVERLAP_MAX`) → rendu (`clipper.render_clip`, un appel ffmpeg : crop suivi + scale + sous-titres incrustés). **Toute la géométrie de cadrage a déménagé dans `speaker.py`** (entrée dédiée juste en dessous) : `clipper` l'importe, jamais l'inverse. Ce qui reste ici du cadrage : `render_clip` appelle `speaker.analyze_framing` quand `speaker_cuts` est vrai, retombe sinon sur `track_faces` + `speaker.track_to_segments` (suivi du plus grand visage, le comportement d'avant), et `crop_supports_eval` sonde la ffmpeg installée. Fonctions pures et testées : `sentences`, `snap_to_speech`, `rank_moments`, `moment_score`, `build_ass` (sous-titres karaoké, mot en cours en rouge, chaque `Dialogue` tenant jusqu'au mot SUIVANT du groupe — le borner sur la fin du mot éteint la ligne à chaque respiration ; style `Anton`, la police OFL embarquée que beatsync associe au nom logique « impact », avec `fontsdir=` passé au filtre `subtitles` — « Impact » serait résolu par fontconfig et libass lui substituerait silencieusement une sans-serif), `ass_time` (horodatage ASS H:MM:SS.cc — **tronque** les centièmes au lieu d'arrondir : `round()` ferait passer 1,999 s à `.100`, trois chiffres là où ASS en attend deux, et le sous-titre disparaît), `ffmpeg_path` (chemin utilisable **à l'intérieur** d'une chaîne de filtre ffmpeg — existe pour Windows : le `:` de `C:\` est un séparateur d'options de filtre, et l'apostrophe introduite pour l'échapper refermerait la chaîne `subtitles='...'` si elle n'était pas elle-même échappée en dernier), `transcript_digest`, `moment_text`. Quatre fonctions d'I/O en périphérie : `transcribe` (sonde `has_audio` **avant même de charger le modèle Whisper** — le lot 1 ne traite QUE le contenu parlé ; une source sans piste audio ou sans parole passe la source en `failed` avec un message explicite plutôt que de faire planter faster-whisper avec une `IndexError` opaque), `track_faces` (OpenCV, 2 fps comme le scan beatsync), `render_clip`, et `_call_json` — **n'est PAS `beatsync._call_llm`** : celui-ci a le prompt punchline codé en dur et une signature sans schéma, `_call_json` prend `system`/`user`/`schema` en paramètres. Il réutilise en revanche `beatsync._llm_backend` et `beatsync._load_dotenv`, et honore `LLM_FALLBACK` avec la même mécanique (dict nom → nom de fonction résolu par `globals()`), pour que `LLM_BACKEND` pilote les deux sous-systèmes de la même façon. L'API Messages d'Anthropic n'a pas de paramètre `seed` : la seed est injectée dans le texte du prompt, comme le fait déjà `beatsync._punchline_user_prompt`. Les couleurs ASS sont en **BGR**, pas en RGB (`#ff1e46` s'écrit `&H461EFF&` — R et B inversés) — l'inverser donne du bleu, pas une erreur visible au test. `clip_source.process` écrit le statut en base à chaque étape (`transcribing`/`analyzing`/`rendering`/`done`/`failed`) pour que l'UI suive l'avancement ; une analyse qui ne produit aucun clip passe la source en `failed`, et les clips du run précédent ne sont supprimés qu'**après** avoir vérifié qu'il y a des candidats à rendre — sans quoi une relance avec le LLM éteint effaçait un bon lot en annonçant un succès. `SEED` est fixe (1337, pas par variante comme beatsync) : la reproductibilité vaut au niveau de la source, pour pouvoir comparer un réglage à un autre. Format de sortie du lot 1 : vertical 1080×1920 en dur, pas de preset de format. `clipper.DEFAULTS` et `beatsync.DEFAULT_CONFIG["clipper"]` sont deux littéraux **volontairement dupliqués** (il n'existe aucune constante partagée : importer `clipper` depuis `beatsync` inverserait la dépendance et paierait cet import à chaque `import beatsync`), tenus alignés par le test `test_clipper_defaults_match_beatsync` — sans quoi le CLI et l'interface divergeraient en silence. Fiche détaillée, avec ce qui reste hors périmètre du lot 1 : [`docs/fiches/10-clipper.md`](docs/fiches/10-clipper.md).
- `speaker.py` — **cadrage du clipper** : qui tient l'image à chaque instant, et comment cette décision devient une géométrie de crop pour FFmpeg. La dépendance est **à sens unique** — `clipper` importe `speaker`, jamais l'inverse : un import croisé rendrait les deux modules inchargeables séparément, et `speaker` est le plus bas niveau des deux. Comme dans `clipper`, le cœur est pur (pistes, filtres, timeline, segments, expression) et seule `analyze_framing` fait de l'I/O.
  **DOMAINE DE VALIDITÉ, à lire avant d'essayer** : le recadrage sur le locuteur marche sur du contenu **déjà monté en plans découpés** — mesuré sur la fenêtre 150-180 s de la source d'essai : 7 coupes relevées et toutes vraies, zéro fausse, aucune piste d'habillage retenue, plans de médiane 4,6 s. Il marche **mal sur du plan large filmé à l'épaule** — mesuré sur la fenêtre 60-90 s de la même source : 10 des 16 segments collés au plancher `MIN_SHOT`, parce que le signal d'agitation y est dominé par le mouvement de caméra (corrélation hauteur de visage / agitation : **−0,64**, voir la limite documentée dans `_mouth_activity`). Le réglage `speaker_cuts` (défaut `True`) est le **repli** : à `False`, `render_clip` revient au suivi lissé du plus grand visage. C'est la porte de sortie quand la détection se comporte mal sur un contenu donné, pas un mode dégradé honteux.
  Suivi : `iou` (recouvrement rapporté à l'union) et `link_tracks` (appariement glouton par recouvrement décroissant, `IOU_MIN` 0,3 — le meilleur couple figé d'abord, pour qu'un visage ne vole pas l'appariement d'un autre quand deux personnes se rapprochent). **Une piste non appariée n'est PAS close** : la cascade rate régulièrement un visage (tête tournée, flou de mouvement) et rouvrir une piste ferait passer la même personne pour une nouvelle — donc une coupe injustifiée. Elle reste candidate sur sa dernière position connue, mais avec une **borne d'ancienneté** (`TRACK_MAX_AGE`, 30 images ≈ 3 s à la cadence prévue) : sans elle, une personne qui sort du cadre et une autre qui arrive longtemps après au même endroit fusionnent sous la même identité.
  `usable_tracks` — trois filtres, chacun motivé par un contre-exemple réel de la source d'essai (l'habillage figé du bord gauche : quatre vignettes de scores incrustées, immobiles pendant des minutes) : (1) `MIN_DETECTIONS` = 2 **passes de détection** — attention à l'unité, entre deux passes les rectangles sont tenus à leur dernière position, si bien que compter les images laissait passer tous les faux positifs (mesuré sur 60-90 s : 39 pistes, 23 vues sur une seule passe, zéro rejetée) ; (2) `MIN_FACE_FRACTION` = 0,06 de la hauteur d'image, jugé sur la **médiane** des hauteurs et non le maximum — sinon un seul faux positif de grande taille sauve une piste composée à 90 % de vignettes ; (3) `STATIC_FRACTION` = 0,15 de la hauteur du rectangle, rapporté à sa propre taille parce qu'une tolérance absolue ne peut pas servir les deux échelles (10 px sur une vignette de 70 px c'est de l'habillage, sur un visage de 400 px c'est un frémissement) — les trois faux visages de l'habillage parcourent 2,6 / 5,9 / 10,2 % de leur hauteur contre 19 % pour le vrai interlocuteur le plus statique, le seuil est posé au milieu de cet écart ; et il ne s'applique qu'à partir de `_STATIC_MIN_DETECTIONS` = 4 passes, en deçà l'immobilité ne prouve rien.
  `speaker_timeline` — qui tient le cadre, image par image, sur l'agitation moyennée dans une fenêtre `ACTIVITY_WINDOW` (0,6 s : assez long pour lisser une syllabe, assez court pour réagir à une prise de parole). Deux garde-fous **contre le clignotement**, le défaut qui se lit comme un bug et non comme un montage : `SWITCH_MARGIN` (1,5 — le prétendant doit être une fois et demie plus agité que le tenant, sinon deux personnes qui se coupent la parole font osciller le cadre) et `MIN_SHOT` (1,2 s de plan minimum), ramené à `CUT_MIN_SHOT` (0,4 s) sur une coupe de la source, où le saut est masqué — un second plancher est nécessaire, sans lui une rafale de coupes désactive complètement `MIN_SHOT` — et c'est un **assouplissement**, jamais un durcissement : le code prend `min(min_shot, CUT_MIN_SHOT)`, sinon un `min_shot` réglé sous 0,4 s (settings.json édité à la main, non coercé) verrait une coupe *retarder* la bascule. `track_id` ne vaut `None` que faute de **toute** piste : dès qu'une piste existe on tient le dernier cadrage plutôt que de recentrer, y compris en silence total, où recentrer se lit comme une panne. Le plancher ne s'arme (`armed`) qu'au premier choix appuyé sur un score positif — verrouiller le plan sur un choix fait à l'aveugle tiendrait le premier vrai locuteur à l'écart pendant `min_shot`.
  Géométrie : `crop_size` (rectangle 9:16 le plus large qui tienne, les DEUX dimensions paires — une hauteur source impaire ferait échouer l'encodage yuv420p), `crop_segments` (traduit la timeline en segments portant le x de leur début et celui de leur fin ; trois niveaux de repli : rectangles dans le segment → ancrage normal ; piste connue mais aucun rectangle dans ce segment → **on tient la position connue la plus proche en temps** plutôt que de recentrer, la personne est toujours là ; piste inconnue → centre, là il n'y a rien à tenir), `crop_expr` (**interpole à l'intérieur d'un segment et saute sec entre deux** : c'est la coupe demandée, un glissement d'un visage à l'autre se lirait comme une dérive ; `_ramp` émet `2*floor((x0+pente*t)/2)`, le pair étant exigé par le chroma yuv420p ; `_merge_static` fusionne les paliers immobiles pour ne pas consommer `MAX_STEPS` pour rien, et au-delà du plafond la liste est **décimée** — un segment gardé sur k, qui absorbe ceux qu'il remplace, bornes recollées — et non tronquée : le cadre suit l'orateur jusqu'au bout du clip, simplement plus grossièrement. Tronquer en prolongeant le dernier segment retenu figeait le cadre sur toute la queue du clip (300 segments sur 150 s : juste 59,5 s puis immobile 90 s, l'orateur sortant du champ sans y revenir)), `smooth_track` (moyenne glissante + **zone morte** `DEAD_ZONE`, en pixels SOURCE : `render_clip` passe `DEAD_ZONE * crop_w` et non `* OUT_W`, sans quoi la même constante vaudrait 21 % de l'image finale en 720p contre 7 % en 4K — utilisée par le seul chemin de repli, avec `track_to_segments`), et `expr_needs_eval` — **piège** : `crop_expr` peut rendre une rampe **sans aucun `if(`** (segment unique non constant), donc tester `"if(" in expr` figerait le cadre en silence sur les ffmpeg ≤ 7 ; le seul test fiable est « est-ce un entier littéral ».
  `analyze_framing` (I/O) — décode le clip **une seule fois, séquentiellement, jamais par `seek`** : 1,4 ms l'image contre 45 ms, mesuré sur la source d'essai, et c'est ce renversement qui rend abordables les 10 images/s de `FRAME_FPS` — or la parole agite la bouche à 5-10 Hz, en dessous de 10 images/s l'information n'existe tout simplement pas (les 2 images/s du scan beatsync ne suffisent pas). **`FRAME_FPS` est une cadence VISÉE, pas obtenue** : `keep_every` est entier, donc la cadence réelle vaut `source_fps / keep_every` (12,5 sur du PAL, 12 sur du cinéma, 11,988 sur du NTSC) — d'où `sampling_cadence`, sans laquelle la timeline entière est étirée de 25 % sur une source à 25 images/s et le cadre suit l'orateur avec un retard croissant ; elle ramène aussi à `FALLBACK_FPS` une cadence source inexploitable — 0, négative, ou **NaN**, que certains conteneurs rendent et qu'un `or 30.0` n'attrape pas (NaN est truthy) : `int(round(nan))` levait alors et le clip était perdu au lieu d'être cadré au centre. La détection Haar ne tourne qu'une fois toutes les `DETECT_EVERY` (0,5 s) et en demi-résolution (`DETECT_SCALE`, 8 ms contre 25 ms pour la même détection à ces tailles de visage) ; entre deux passes les rectangles sont tenus et l'on n'y mesure que l'agitation. `detect_cuts` relève les coupes du montage d'origine sur un critère **relatif à la distribution du clip** (`CUT_RATIO` = 5 × la médiane des écarts inter-images : sur 60-90 s, écart médian 0,037, vraies coupes 0,189-0,217, pics de flou de filé jusqu'à 0,170 — un seuil absolu bas ne les sépare pas), plus un plancher absolu `CUT_FLOOR` = 0,15 indispensable quand le clip est calme (sur 150-180 s, médiane 0,017 : 5 × médiane relèverait 17 candidats dont 10 faux ; le plancher coûte une vraie coupe sur huit, ce qui est le bon compromis — une coupe manquée laisse simplement `MIN_SHOT` s'appliquer, une fausse coupe autorise un plan de 0,4 s là où aucun saut du montage ne le masque). Une source illisible rend un cadrage centré plutôt que d'échouer — l'usine ne bloque jamais — mais le **signale via `log`**, qui reçoit aussi une ligne de fin d'analyse (nombre de plans, de coupes et de pistes retenues) : sans ça, un fichier corrompu est indiscernable d'une vidéo sans visage — les deux rendent la même expression constante — et le journal du job reste muet plusieurs secondes par clip, ce qui se lit comme un blocage.
  **La cascade est frontale** (`haarcascade_frontalface_default.xml`) : un intervenant de profil n'est pas détecté du tout, sa piste est simplement tenue à sa dernière position — d'où le repli n°2 de `crop_segments`, qui n'est pas un cas rare mais le cas courant. Corollaire mesuré à l'œil sur 150-180 s : les 4 pistes utilisables ne couvrent que 4,7-18,9 s des 30 s, et les deux tiers du clip sont cadrés par cette position tenue. **Constantes empiriques**, calées sur une seule source (`data/clipper/football-magouilles-compagnie-ep12`) et à ne pas déplacer sans refaire la mesure : `CUT_RATIO`, `CUT_FLOOR`, `MIN_DETECTIONS`, `MIN_FACE_FRACTION`, `STATIC_FRACTION`, `_STATIC_MIN_DETECTIONS`. Les autres (`IOU_MIN`, `TRACK_MAX_AGE`, `ACTIVITY_WINDOW`, `SWITCH_MARGIN`, `MIN_SHOT`, `CUT_MIN_SHOT`, `DEAD_ZONE`) sont des choix de confort visuel, pas des mesures.
- `beatsync.py` — le montage, découpé en fonctions indépendantes et testables, pensées pour être éclatées en modules plus tard :

- `analyze_audio(track_path)` — librosa : grille de beats (timestamps en s), BPM, enveloppe d'énergie RMS. Import librosa paresseux (coûteux, inutile pour la logique pure)
- `find_drop(analysis, config)` — **pure** : drop = max de contraste d'énergie avant/après (fenêtres ±8 s), calé sur un beat ; None si énergie plate. Sans `--start`, main cadre la fenêtre sur `[drop - buildup, drop + reste]`
- `load_clips(folder)` — métadonnées des clips via ffprobe ; liste **triée par nom** (déterminisme)
- `scan_clips(clips, cache_dir=None)` / `_scan_one` / `classify_frames` / `usable_intervals` / `_char_presence` — frames 640x360 à 2 fps via FFmpeg (miniatures 32x18 par blocs pour couleur/mouvement). Avec `cache_dir`, résultat par clip mis en cache (clé md5 du chemin, invalidé par mtime, tolérant à la corruption → cache miss) : on ne re-décode pas 30 clips à chaque génération → exclusion cartes orange Crunchyroll, frames noires, statiques, plages à mouvement moyen < 0.05 (pans d'établissement) et plans sans personnages. Présence = visage animé (cascade `assets/lbpcascade_animeface.xml`, poids 1.0) OU contours d'encre (poids 0.6), détectés dans la **bande centrale 40 %** seulement (ce qui survit au crop 9:16 — élimine le logo Crunchyroll du coin par construction). Présence 0 = plan vide → coupe la plage. `classify_frames`/`usable_intervals` sont **pures et testées**. `intervals: []` = clip scanné inutilisable (≠ clé absente = pas scanné, clip entier utilisable). OpenCV pinné `<5` (CascadeClassifier retiré en 5.x). `content_rect` (**pure**) détecte les bandes noires (letterbox/pillarbox) sur les frames déjà décodées : profil de luminance par ligne et par colonne, 95ᵉ percentile sur les frames (pas le maximum — un sous-titre incrusté dans la bande masquerait la détection), segments continus depuis les bords seulement (`_edge_runs`). Une bande sous `BAR_MIN_FRACTION` (1,5 %) est du bruit de bord ; des bandes au-delà de `BAR_MAX_TOTAL` (30 %) sont une scène sombre, pas un letterbox → `None`. Le rectangle est stocké en fractions dans `clip["crop"]`, et `ratio` est corrigé pour décrire le **contenu** — sans quoi un film 2.35:1 letterboxé passe pour du 16:9 et les seuils de layout (`split`/`blur`) restent faux. `SCAN_CACHE_VERSION` invalide les caches antérieurs à ce changement.
- `build_edl(analysis, clips, config, seed)` — **logique pure, sans I/O ni rendu** : construit l'Edit Decision List. Rythme « energy » : percentile d'énergie de chaque beat (sur le morceau ENTIER) → intervalle 4/2/1 beats ; `--cut-every N` force le mode fixe. Avec `drop_time` : coupe garantie pile sur le drop, strobo 1 beat pendant 16 beats, sections buildup/drop, effets par segment (`zoom`/`flash`/`shake` — déterministes à seed égal). `effects.blackout` (opt-in, défaut `False`) : les **zones de montée** deviennent une alternance éclair / écran noir au pas de `blackout_beats` (0,5 beat par défaut, borné `[0.25, 2.0]` côté serveur). `strobe_zones` (**pure et testée**) décide où strober : **avec drop**, une zone unique couvrant tout le build-up ; **sans drop** (preset chill `section: "calm"`, où `resolve_window` ne cherche même pas de drop), une zone par impact de `speed_ramp`, couvrant les `blackout_lead` beats qui le précèdent (2 par défaut, borné `[0, 8]` côté serveur — 0 désactive le repli, au-delà d'`impact_beats` les zones se rejoindraient). Les zones sont bornées par le candidat de scène de fin, qui réécrit les frontières plus bas et laisserait sinon un long noir en guise de conclusion. `blackout_boundaries` (**pure et testée**) réécrit la grille de chaque zone en comptant à rebours depuis son ancre, ce qui garantit que le segment s'y terminant est un éclair d'image — l'impact tombe sur une image, jamais sur du noir ; la frontière du drop conserve son indice de beat pour que la relance accélérée (`speed_ramp.fast`) reste calculable APRÈS le drop — pas pour le ralenti d'anticipation qui le précède : ce « gasp » ne s'applique plus une fois le strobe actif, remplacé par l'éclair qui termine le build-up. Le segment de tête est forcé en image (une vidéo qui s'ouvre sur du noir ressemble à un bug). Les entrées `kind: "black"` sortent de la boucle avant la sélection de clip : ni clip ni cadrage, aucun tirage seedé consommé, aucune matière retirée au catalogue par la mémoire anti-répétition ; les images en sont exclues aussi (un segment sous strobe est toujours un éclair, jamais un plan normal — sans quoi un catalogue riche en images transformerait la montée en diaporama), via le troisième retour de `blackout_boundaries` qui donne les frames de début des segments strobés — et non plus via la section `buildup`, qui ratait le cas sans drop où tout vaut `main`. Double le nombre de segments du build-up ; en pratique l'effet sur le temps de génération est faible, voire négatif à réglages par défaut — le strobe supprime justement le segment ralenti que le flux optique (`speed_ramp.interpolate`) rendait coûteux. `speed_ramp` : ralenti d'anticipation sur le segment qui finit sur un impact, accéléré de relance sur celui qui commence dessus (impacts = le drop, ou le premier beat de la fenêtre, et ses multiples d'`impact_beats`) ; segments plus courts que `min_dur` exemptés. Le « gasp » avant le drop en est un cas particulier — sauf quand le strobe est actif : il remplace alors ce ralenti par l'éclair. `ramp_speed`/`is_impact` sont **pures et testées**. `speed_ramp.slow_beats` : les coupes des N beats précédant un impact sont retirées (`merge_boundaries_before_impacts`, **pure et testée**) pour que le segment ralenti dure assez longtemps pour se voir — sinon le strobo le réduit à un demi-beat. Fait avant la quantification, pour que l'exemption `min_dur` juge la durée fusionnée ; à `slow_beats: 1`, rien n'est retiré. `end_scene` (opt-in) : les N derniers beats de la fenêtre sont réservés à un segment unique portant le climax narratif. `find_final_scene` (**pure**) note les plages du dernier tiers de chaque clip (`FINAL_SCENE_TAIL`) sur duel (`interval_dual_ratio`) + présence + mouvement ; elle retourne `None` si rien n'est exploitable, et le montage se termine alors normalement. L'entrée porte `end_scene: True`, `ramp_slow: True` et `freeze`. `clip_in` pioché uniquement dans les plages exploitables, filtrées par `min_presence`. Mode `chrono` (défaut) : position dans la timeline ≈ position dans l'histoire du clip (mapping proportionnel sur les plages, monotone par clip, jitter seedé) — le drop tombe sur le climax ; `chrono: False` restaure le tirage libre avec préférence mouvement pour les segments intenses. Anti-répétition : `build_edl` mémorise par clip les portions déjà montrées (`consumed`), et `free_windows` (**pure et testée**) n'offre plus que ce qui reste, élargi d'une marge de 0,5 s — deux extraits qui se touchent restent visuellement identiques. La mémoire alimente les trois points de décision (clips utilisables, mapping chrono, tirage libre) ; le mode `chrono` y ajoute un plancher, la fin de la dernière portion consommée. La scène de fin réserve sa portion avant la boucle, pour qu'aucun segment ordinaire ne montre le climax par avance. Deux replis distincts : si aucun clip n'a de fenêtre libre, les plages sont rouvertes en entier pour tous (catalogue épuisé, plutôt que faire échouer le lot) ; si seul le clip précédent reste utilisable, ce sont les AUTRES clips qui sont rouverts en priorité, pour éviter d'enchaîner deux plans du même clip — la coupure visuelle entre deux plans identiques se remarque plus qu'un passage déjà montré revu ailleurs. `frame_extract` (**pure**) : cadrage d'un extrait (fenêtre min 3 échantillons de scan), partagé par le chemin ordinaire et la scène de fin — `focus_x` (centroïde visages/contours) cale le crop, remappé du cadre entier vers le **contenu** quand le clip a des bandes noires (sinon, après rognage, le centre d'intérêt pointerait à côté). Les deux layouts de secours dépendent du **format de sortie** : duel strict majoritaire → `layout: split` seulement si `width/height <= 0.75` ; dispersion σ≥0.18 → `layout: blur` seulement si `ratio_clip >= 2 × (width/height)` — soit 1,125 en vertical (tout 16:9) et 2,0 en carré (un scope seulement). Seul le seuil `blur` s'applique aux images (jamais `split` : le duel n'est noté que sur les clips scannés). Accents : `rgb` sur les impacts, `glitch` seedé sur ~25 % des segments intenses du drop. `snap_end_to_phrase` (pure) étend la fin au multiple de 16 beats après le drop — la musique ne coupe pas en pleine phrase. Images : un asset `kind: "image"` du catalogue n'est monté que sur un segment ≤ `IMAGE_MAX_DUR` (0,6 s), jamais deux fois à moins de 3 segments **visibles** d'écart (les écrans noirs du strobe ne comptent pas dans cet écart) ; le strobe de build-up exclut d'ailleurs les images de son alternance, à vitesse 1.0, avec un Ken Burns dont les sens sont tirés à la seed et un layout déduit du seul ratio (le scan ne tourne pas sur les images)
- `assign_caption_slots` / `generate_punchlines` / `apply_subtitles` — **punchlines incrustées** (« sous-titres générés »). `assign_caption_slots` (pure, testée) regroupe les segments en créneaux ≥ `min_dur` (une punchline change à la coupe mais reste lisible). `generate_punchlines` appelle le LLM via `_call_llm` (isolé pour le mock), qui **dispatche sur un backend** choisi par `LLM_BACKEND` : `lmstudio` par défaut (`_call_lmstudio` : serveur local compatible OpenAI, HTTP stdlib, coût nul — endpoint/modèle via `LMSTUDIO_BASE_URL`/`LMSTUDIO_MODEL`, `seed` transmis pour la reproductibilité) ou `anthropic` (`_call_anthropic` : SDK Anthropic, `output_config.format`, `claude-opus-4-8`). `LLM_FALLBACK` nomme un backend de repli si le primaire échoue. Mis en cache par (backend, modèle, préprompt, count, seed) → reproductible ; **dégrade en `[]` en cas d'échec** (l'usine ne bloque jamais sur le LLM). `apply_subtitles` pose `entry["caption"]` par créneau. `subtitles.mode` vaut `"llm"` (punchlines générées, le cas par défaut ci-dessus) ou `"fixe"` (caption unique écrite à la main dans `subtitles.text`, posée telle quelle sur tout l'EDL, sans créneaux ni appel LLM). `subtitles.x`, `y`, `size` règlent le placement du drawtext pour **les deux** modes : le texte est centré sur son point d'ancrage exprimé en fraction d'écran. Le backend Anthropic requiert `ANTHROPIC_API_KEY` ; le backend LM Studio requiert le serveur local lancé. CLI : `--subtitles "préprompt"`. Le rendu incruste via drawtext (police Impact, bas-centré, contour) APRÈS les accents RGB pour rester net.
- `render(edl, audio_path, output_path, config)` — un segment encodé par entrée d'EDL (vf construit par segment selon les effets, dont le drawtext de la punchline) puis concat en copie de flux. Chaque segment est forcé à un nombre de frames EXACT (`tpad` + `-frames:v`) : sans ça, les sources 23,976 fps rendent quelques ms de moins et le concat accumule une dérive audio/vidéo. La source consommée = `duration × speed`. Écrans noirs : `_segment_input_args` retourne une source `lavfi` (`color=c=black`) — aucun fichier ouvert — et `_segment_filters` sort tôt sur une chaîne minimale (fps, punchline, normalisation, `tpad`) ; `_caption_filter` est extrait pour être partagé par les deux chemins. La punchline est **conservée** sur le noir : la faire clignoter à 2 Hz la rendrait illisible. Segments ralentis : `minterpolate` (flux optique) remplace le `fps=` simple quand `speed < 1` et `speed_ramp.interpolate`, après le cadrage — très coûteux : **×36 l'encodage du segment concerné** (mesuré sur 60 frames de sortie à travers la vraie chaîne de filtres), ce qui donne ×6,1 sur un rendu entier où seule une minorité de segments est ralentie. Le filtre ne parallélise pas (~111 % CPU contre ~440 %), donc il ne s'amortit pas sur les cœurs. Désactivable via `speed_ramp.interpolate`, exposé dans l'éditeur de preset. Images : `_segment_input_args` boucle l'entrée (`-loop 1`, pas de seek). Figé de fin : une entrée portant `freeze` consomme `(duration − freeze) × speed` de source (`_segment_input_args`), sans le rab de seek de 0,5 s (ce rab, amplifié par le ralenti, annulait le figé), et `tpad=stop_mode=clone:stop_duration=1+freeze` clone la dernière image pour combler. Aucun filtre dédié, et `-frames:v` garde le compte exact. Bandes noires : l'entrée porte `crop` en pixels et des `clip_w`/`clip_h` décrivant le contenu ; `_segment_filters` rogne en **tête** de `pre`, avant le `delogo` — qui se recale donc au passage, puisqu'il compte en fractions de ces dimensions.
- `main()` — CLI argparse ; sans `--start`, cadrage auto sur le drop (buildup 10 s + drop) ; fenêtre de 30 s par défaut (sortie format TikTok). `format` (`"vertical"` 1080×1920 | `"carre"` 1080×1080 | `"horizontal"` 1920×1080, constante `FORMATS` — dont argparse dérive ses `choices`) pose `width`/`height` via `apply_format`, appelée en tête de `generate_video` — le point de passage unique du CLI et de l'usine par niche. Format inconnu = vertical. CLI : `--format`

## Contrainte centrale : reproductibilité

Relancer avec la même seed doit produire exactement la même vidéo. Trois garde-fous à ne pas casser :

1. `load_clips` trie les fichiers par nom (l'ordre du filesystem n'est pas déterministe)
2. `build_edl` utilise un `random.Random(seed)` local, jamais le RNG global
3. Le rendu FFmpeg passe des flags `bitexact` pour neutraliser les métadonnées horodatées

Autre invariant : les timestamps de cut sont quantifiés sur la grille de frames (fps de la config) dans `build_edl`, pas dans `render`, pour que l'erreur ne s'accumule pas et que ce soit testable.
